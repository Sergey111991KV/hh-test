# Контур — мини-CRM «Объекты и задачи»

Мини-CRM для строительной команды. Руководитель ведёт объекты, назначает исполнителей и принимает работу. Исполнитель видит свои задачи и меняет их статус по рабочему процессу. История действий сохраняется в базе.

## Статус для приёмщика

Репозиторий содержит приложение, схему базы, демо-данные и публичные тестовые логины с паролями. **Подключённого Supabase-проекта и опубликованной демо-ссылки в репозитории нет.** Чтобы логины заработали, создай указанные ниже аккаунты в отдельном тестовом Supabase-проекте и подключи его по шагам дальше.

Для входа необходимо один раз выполнить разделы «Настроить Supabase» и «Создать тестовые учётные записи». После этого приёмщик сможет проверить сценарии из раздела «Сценарий приёмки». Если принимающей стороне нужна уже работающая ссылка без настройки базы, владелец должен отдельно предоставить адрес развернутого приложения и пароли к созданным тестовым аккаунтам.

## Возможности

- Вход по email и паролю; форма открытой регистрации отсутствует.
- Руководитель создаёт и редактирует объекты и задачи, назначает исполнителей, принимает задачи и возвращает их с комментарием.
- Исполнитель видит назначенные ему задачи и связанные объекты, берёт задачи в работу, отправляет их на проверку и продолжает после возврата.
- Карточка задачи показывает исполнителя, объект, описание, доступные действия и хронологию переходов статуса.
- Удаление объектов и задач мягкое: они скрываются из активного списка, записи и история остаются в базе.
- Роли, доступ к строкам и допустимые переходы повторно проверяются в PostgreSQL через RLS и SQL-функции.

## Требования

- Node.js 20.19 или новее.
- pnpm 9 или новее.
- Аккаунт Supabase с правом создать проект и пользоваться SQL Editor.

## Быстрый запуск из GitHub

```bash
git clone https://github.com/Sergey111991KV/hh-test.git
cd hh-test
node --version
corepack enable
pnpm install --frozen-lockfile
```

Если команда `pnpm` недоступна, активируйте её через Corepack:

```bash
corepack prepare pnpm@9.4.0 --activate
```

`node --version` должен показать `v20.19.0` или новее. Дальше настройте Supabase по шагам ниже. Приложение без рабочей базы покажет экран «Подключите рабочее пространство»; войти в нём нельзя.

## Настроить Supabase

### 1. Создать проект и взять клиентские параметры

1. Создайте отдельный проект Supabase для приёмки и дождитесь готовности базы.
2. Откройте **Connect** в панели проекта и скопируйте **Project URL** и **Publishable key**. Эти значения используются в браузере приложения.
3. Не копируйте в приложение **Secret key**, legacy `service_role` или пароль базы. Эти секреты дают расширенный доступ и не должны попадать во фронтенд или Git. Подробнее: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

### 2. Применить миграцию

1. В панели Supabase откройте **SQL Editor** и создайте новый запрос.
2. Скопируйте туда целиком файл [`supabase/migrations/202611060001_initial_schema.sql`](supabase/migrations/202611060001_initial_schema.sql) и нажмите **Run**.
3. Выполняйте миграцию один раз на пустом проекте. Не запускайте её повторно поверх уже созданных таблиц.

Миграция создаёт профили, объекты, задачи, историю статусов, RLS-политики, триггеры и функции для операций. Профиль для каждого нового Auth-пользователя создаётся автоматически с ролью исполнителя.

### 3. Отключить открытую регистрацию

В настройках Supabase Auth отключите **Allow new users to sign up**. Провайдер **Email** должен оставаться включённым: пользователи будут входить по паролю. Добавлять аккаунты для приёмки нужно из панели Supabase, а не через форму приложения. Название и расположение настройки могут меняться; см. [Supabase Auth configuration](https://supabase.com/docs/guides/auth/general-configuration).

### 4. Создать тестовые учётные записи

В панели проекта откройте **Authentication → Users → Add user → Create new user**. Создайте подтверждённые аккаунты с email и паролями из таблицы. Для адресов `example.com` не используйте отправку приглашения: почтовый ящик для них не подготовлен.

| Роль | Email для входа | Тестовый пароль | Имя в демо |
| --- | --- | --- | --- |
| Руководитель | `manager@example.com` | `Kontur-Demo-Manager-2026!` | Анна Смирнова |
| Исполнитель 1 | `executor1@example.com` | `Kontur-Demo-Executor1-2026!` | Илья Петров |
| Исполнитель 2 | `executor2@example.com` | `Kontur-Demo-Executor2-2026!` | Мария Волкова |

Это публичные демонстрационные данные: любой, кто видит репозиторий, может прочитать пароли. Используйте их только в отдельном проекте с вымышленными данными. Не применяйте эти пароли к личным или рабочим аккаунтам. После выполнения миграции создание Auth-пользователя автоматически добавит его профиль. Создайте всех троих **до** запуска демо-данных. Официальная справка: [Supabase Auth users](https://supabase.com/docs/guides/auth/users).

### 5. Загрузить демо-данные

1. Откройте новый запрос в **SQL Editor**.
2. Скопируйте целиком [`supabase/seed/demo.sql`](supabase/seed/demo.sql) и нажмите **Run**.

Скрипт задаёт имена и роли аккаунтов, создаёт три объекта и шесть задач в разных статусах. Его можно выполнять повторно: активные объекты и демо-задачи не дублируются. Для ожидаемых чисел из сценария приёмки используйте новый проект без других данных.

### 6. Заполнить локальную конфигурацию

В корне репозитория создайте `.env.local` на основе `.env.example`:

```bash
cp .env.example .env.local
```

Заполните файл значениями своего Supabase-проекта:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your_key
```

Значения в примере — заглушки, с ними приложение не подключится. URL и publishable key выдаются конкретному Supabase-проекту; в текущем репозитории реальных ключей нет. `.env.local` игнорируется Git. Не добавляйте в клиент пароль базы, Secret key или `service_role`. Publishable key предназначен для клиента; безопасность строк обеспечивает RLS. Подробнее: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys). Если меняете переменные после запуска Vite, остановите и запустите сервер заново.

## Запустить и проверить

Запустите приложение:

```bash
pnpm dev
```

Откройте адрес, который напечатает Vite; обычно это <http://localhost:5173/>. Войдите email и паролем, заданными при создании аккаунтов в Supabase.

### Пароли

Пароли для трёх тестовых пользователей приведены в таблице выше и намеренно опубликованы вместе с исходным кодом. Они не являются паролями к самому Supabase-проекту, аккаунту GitHub или хостингу. Реальный URL приложения появится только после настройки Supabase и публикации на хостинге.

### Сценарий приёмки

В свежей базе после загрузки `demo.sql` руководитель должен видеть **3 объекта и 6 задач**. У каждого исполнителя будет по **3 назначенные задачи**.

1. **Вход руководителя.** Войдите как `manager@example.com`. Проверьте список объектов, все задачи и имена исполнителей. Откройте задачу «Проверить гидроизоляцию паркинга» в статусе «На проверке».
2. **Возврат на доработку.** Нажмите «На доработку». Без комментария кнопка возврата недоступна. Введите замечание и верните задачу. Статус станет «На доработке», а в истории появятся переход, автор, время и комментарий.
3. **Создание и редактирование задачи.** Создайте задачу для одного из объектов и назначьте `executor1@example.com`. Убедитесь, что задача появилась в списке. Откройте карточку, выберите «Изменить», поправьте название или описание и сохраните.
4. **Вход исполнителя 1.** Выйдите из аккаунта руководителя и войдите как `executor1@example.com`. Видны только его назначенные задачи. Возьмите задачу «Проверить ведомость арматуры» в работу, затем отправьте её на проверку. В карточке должна обновиться история.
5. **Вход исполнителя 2.** Войдите как `executor2@example.com`. Проверьте, что задачи исполнителя 1 не отображаются. Для задачи «Доработать схему временного освещения» нажмите «Начать доработку».
6. **Приёмка результата.** Снова войдите как руководитель. Примите задачу, ожидающую проверки. Статус станет «Принята», а действие сохранится в истории.
7. **Права ролей.** У исполнителей нет кнопок создания и редактирования. Исполнитель видит только свои задачи; проверить ограничение строк можно на разных аккаунтах из таблицы выше.

Действия удаления объектов и задач необязательны для базовой приёмки: они убирают запись из активных списков, но оставляют её в базе.

## Проверки проекта

В репозитории нет отдельного автоматизированного набора тестов. Доступные локальные проверки:

```bash
pnpm build
```

Команда выполняет проверку TypeScript и production-сборку в `dist/`. Для просмотра этой сборки локально:

```bash
pnpm preview
```

Проверка реального входа, RLS и операций требует заполненного `.env.local`, применённой миграции и тестовых аккаунтов в Supabase.

## Публикация приложения

Исходный код расположен в [GitHub-репозитории](https://github.com/Sergey111991KV/hh-test), ветка `main`. Само приложение пока не опубликовано на веб-хостинге.

Для публикации на Vercel:

1. Импортируйте этот GitHub-репозиторий в Vercel.
2. Укажите команду сборки `pnpm build` и каталог публикации `dist`.
3. В настройках окружения проекта добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` из того же Supabase-проекта, куда загружена схема и демо-данные.
4. Запустите Deploy. Файл [`vercel.json`](vercel.json) содержит перенаправление для SPA.
5. Укажите полученный URL в настройках URL сайта Supabase Auth, чтобы ссылки Auth вели на опубликованное приложение.

Аналогично проект можно собрать в Netlify; для SPA есть [`netlify.toml`](netlify.toml). Не публикуйте сайт с пустой базой или без тестовых аккаунтов, если ожидается рабочая демонстрация.

## Устройство доступа и переходы статусов

| Текущий статус | Следующий статус | Кто может выполнить |
| --- | --- | --- |
| Новая | В работе | Назначенный исполнитель |
| В работе | На проверке | Назначенный исполнитель |
| На проверке | Принята | Руководитель |
| На проверке | На доработке | Руководитель; комментарий обязателен |
| На доработке | В работе | Назначенный исполнитель |

RLS ограничивает чтение объектов, задач и истории. Роль, назначение исполнителя и допустимый переход повторно проверяются функциями и триггерами PostgreSQL. История статусов не разрешает приложению изменять или удалять записи.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Экран «Подключите рабочее пространство» | `.env.local` существует в корне, содержит URL и publishable key, после изменения Vite перезапущен. |
| Не удаётся войти | Пользователь создан в нужном Supabase-проекте, email подтверждён, пароль введён тот, что был задан при создании. |
| «Профиль не настроен» | Пользователя создали после миграции. Проверьте наличие его строки в `public.profiles`; при создании пользователя после миграции профиль добавляет Auth-триггер. |
| Пустой список задач | Демо-данные запущены после создания трёх аккаунтов именно в этом проекте Supabase. |
| Ошибка `relation does not exist` | Миграция выполнена в подключённом проекте и завершилась без SQL-ошибок. |
| Один и тот же SQL seed запускается снова | Это безопасно для активных демо-записей; миграцию повторно не запускайте. |
